# 早会日报第四份报告集成实施计划

## 一、建设目标

在现有精益早会日报的三份报告基础上，新增第四份《班次/班组绩效对比分析报告》：

1. 基础日报
2. 趋势分析
3. 改善建议
4. 班次/班组绩效对比

第四份报告始终以原始日报中的白班、夜班数据为基础，并根据班组关系是否有效自动选择分析维度：

- 有有效班组关系：按班组及组长维度分析。
- 无班组关系或关系无效：按白班、夜班维度分析。

班组关系是增强信息，不再是第四份报告生成的前置条件。

## 二、当前数据现状

### 2.1 日报原始数据

现有日报数据已经包含部分班次信息：

- 设备运转率包含白班、夜班或“早班（单班次）”。
- 质量检验包含 `classType` 或检验时间。
- 点检、报警、报修包含业务发生时间，可以判断班次。
- 暂无 `teamId`、`teamName`、`leaderName`。

日报数据能够独立支持白班、夜班维度分析；班组配置只用于进一步将班次表现归属到班组和组长。

### 2.2 班组班次配置

现有班组班次配置包含：

- `lineId`、`lineName`
- `teamId`、`teamName`
- `schedulingDate`
- `classId`、`className`
- `scheduledDevices`
- 班组名称括号中的组长姓名

它可以提供：

```text
生产日期 + 产线 + 班次
          ↓
班组 + 组长 + 设备范围
```

## 三、现阶段处理方案

在日报拉参完成后、正式数据预处理前，先识别原始数据中的白班、夜班，再尝试加载班组班次配置：

```text
日报原始数据
        +
班组班次配置
        ↓
识别白班、夜班指标
        ↓
尝试按生产日期、lineId、设备和班次关联班组
        ↓
执行现有数据预处理
        ↓
将日报数据和候选班组配置提供给大模型
        ↓
大模型判断按班组还是按班次生成第四份报告
```

前三份报告继续使用原有逻辑；第四份报告始终读取日报班次指标。当前的 `teamScheduleContext`完全由AI服务根据本地班组配置临时构造，不要求上游原始接口提供该字段。

第四份报告的模型判断规则：

```text
模型确认候选班组配置与当前日期、产线、设备和班次存在明确对应关系
→ 输出班组及组长绩效对比

模型无法确认班组对应关系，或没有提供候选班组配置
→ 输出白班与夜班绩效对比
```

预处理程序不预先设置分析维度，也不代替模型判断班组关系是否可用。

## 四、注入数据结构

在日报根节点增加：

```json
{
  "teamScheduleContext": {
    "productionDate": "2026-07-19",
    "lineId": 1,
    "mappingSource": "班组班次配置",
    "teams": [
      {
        "teamId": 3,
        "teamName": "铸带线A班组",
        "leaderName": "陈明浪",
        "classId": 1,
        "className": "白班",
        "classCode": "DAY",
        "devices": [
          {
            "deviceId": 118,
            "deviceName": "1#铸带线"
          }
        ]
      },
      {
        "teamId": 4,
        "teamName": "铸带线B班组",
        "leaderName": "陈昌武",
        "classId": 2,
        "className": "夜班",
        "classCode": "NIGHT",
        "devices": [
          {
            "deviceId": 118,
            "deviceName": "1#铸带线"
          }
        ]
      }
    ]
  }
}
```

`teamScheduleContext`是AI服务根据本地配置筛选后注入的候选班组信息。该字段允许为空或不存在，由大模型结合日报班次数据判断是否采用班组维度。

当前组长姓名从本地配置的班组名称括号中提取。

## 五、班组配置读取

### 5.1 配置位置

将班组配置保存在：

```text
backend/config/team_schedule.json
```

通过环境变量配置实际路径：

```text
TEAM_SCHEDULE_CONFIG_PATH=backend/config/team_schedule.json
```

当前按排班周期更新配置文件。本计划仅覆盖使用本地班组配置的临时方案，不预设上游原始接口会增加 `teamScheduleContext`。

班组配置不存在或没有筛选到候选记录时，不注入班组关系；大模型根据原始日报中的白班、夜班数据生成班次维度报告。

## 六、关联与校验规则

### 6.1 关联主键

优先使用：

```text
生产日期 + lineId + deviceId + 标准班次
```

只有工序级数据时使用：

```text
生产日期 + lineId + 标准班次
```

### 6.2 班次标准化

| 原班次 | 标准班次 |
|---|---|
| 白班、早班 | `DAY` |
| 夜班、晚班 | `NIGHT` |
| 早班（单班次） | `DAY`，同时标记单班制 |

### 6.3 夜班跨日

按生产日期归属：

```text
当日18:00—次日06:00 → 当日夜班
```

例如，2026-07-20 02:30发生的事件归属于2026-07-19夜班。

### 6.4 候选班组配置筛选规则

- `teamScheduleContext.productionDate`与 `meta.period`一致。
- `teamScheduleContext.lineId`与 `meta.lineId`一致。
- 同一日期、产线、设备、班次只能对应一个班组。
- 班组设备ID应能与日报设备ID匹配。
- 白班、夜班设备范围不一致时，只对共同设备进行直接比较。
- 只有一个班次时，不生成虚假的白夜班排名。

预处理只按照日期、产线等确定性条件筛选候选配置，不输出“班组关系有效/无效”的业务结论。班组关系最终是否可用于报告，由大模型结合日报数据判断。

## 七、代码改造

### 7.1 新增班组处理模块

新增：

```text
backend/modules/lean_morning_daily/team_schedule.py
```

主要职责：

- 加载班组配置。
- 按日期和 `lineId`匹配排班。
- 标准化班次。
- 临时解析组长姓名。
- 构造并注入 `teamScheduleContext`。
- 校验重复排班和设备范围。

建议函数：

```python
load_team_schedule_config()
normalize_class_name()
extract_leader_name()
build_team_schedule_context()
inject_team_schedule_context()
```

### 7.2 修改日报Worker

修改：

```text
backend/modules/lean_morning_daily/worker.py
```

在拉参成功后、日报预处理前执行：

```python
payload = inject_team_schedule_context(payload)
```

配置缺失或没有候选记录时记录信息日志，不注入班组配置，由大模型按班次维度生成第四份报告。

### 7.3 新增第四份提示词

新增：

```text
backend/modules/daily_report/prompts/lean_morning_daily_report04.txt
```

报告结构：

1. 当日对比结论
2. 核心指标对比
3. 设备表现对比
4. 质量、点检与设备异常
5. 班组/班次表现
6. 次日改善建议
7. 数据口径说明

提示词约束：

- 只能使用输入事实。
- 无数据不能当作0。
- 百分率差异使用“百分点”。
- 不把设备客观故障直接认定为组长责任。
- 历史报修不作为当班新增报修。
- 单班制或数据缺失时不强行比较。
- 不计算无明确规则的综合分。
- 如果班组配置能够与当前日报班次明确对应，则展示班组和组长。
- 如果班组配置缺失、冲突或无法明确对应，则只展示白班和夜班，不虚构班组。
- 必须在“数据口径说明”中写明本次采用班组维度还是班次维度。

### 7.4 修改模板配置

修改：

```text
backend/config/report_templates.yaml
```

增加：

```yaml
- template: "lean_morning_daily_report04.txt"
  output_name: "班次/班组绩效对比"
  use_raw_data: true
  use_ragflow: false
```

第四份报告直接使用预处理后的日报数据，不依赖前三份报告内容。

### 7.5 扩展报告映射

报告字段映射：

```text
第1份 → markdownContent
第2份 → summaryMarkdown
第3份 → kbReportMarkdown
第4份 → 本地数据库 `team_compare_markdown`
```

同步调整：

- `_map_to_callback_fields()`。
- 报告数量日志。
- 错误兜底信息。
- 最终任务返回值。
- 傍晚版仅生成第一份时的跳过逻辑。

```sql

```

## 九、上游回调

第四份报告保存到AI服务本地数据库字段：

```text
team_compare_markdown
```

```text
teamCompareMarkdown
```

由 `backend/clients/upstream_client.py` 统一组装成功回调请求体。

## 十一、测试计划

### 11.1 单元测试

- 中文、英文括号中的组长解析。
- 白班、夜班和单班制标准化。
- 按日期、产线和设备匹配。
- 夜班跨日归属。
- 配置文件缺失。
- 日期或产线无排班。
- 同班次重复班组。
- 设备集合不同。

### 11.2 报告生成测试

- 正常生成四份报告。
- 第四份能够读取原始班次数据。
- 有明确班组对应关系时，模型生成班组及组长维度报告。
- 无法确认班组对应关系时，模型生成白班、夜班维度报告。
- 第四份不调用RAGFlow。
- 缺少班组信息时前三份仍正常。
- 只有一个班次时不生成虚假比较。
- 傍晚版仍只生成第一份报告。

### 11.3 数据库测试

- 新库直接包含新增字段。
- 旧库启动后自动补充字段。
- 第四份报告可以插入和更新。
- 其他报告调用公共Upsert方法不受影响。

### 11.4 回调和回归测试

- 成功回调中包含 `teamCompareMarkdown`。
- 失败回调不填充报告内容字段。
- 原有回调字段和值保持不变。
- 精益早会日报、傍晚版、批量日报和工厂级日报正常。
- 报告查询及持久化正常。
- 执行 `pytest -v`。

## 十三、验收标准

- 白班、夜班正确关联到班组和组长。
- 没有班组关系时仍能按白班、夜班生成完整报告。
- 相同设备核心指标能够正确比较。
- 第四份报告可以独立生成、保存和查询。
- 缺失数据时不虚构组长或绩效结论。
- 前三份报告行为不变。
- 傍晚版和其他报告类型不受影响。
- 数据库新增字段能够正常插入和更新。
- 上游成功回调能够接收第四份报告。
