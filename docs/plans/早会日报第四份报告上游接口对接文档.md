# 早会日报第四份报告上游接口对接文档

## 一、文档目的

本文档用于约定上游日报系统与AI报告服务之间的数据交互方式，以支持新增第四份《班组组长绩效对比分析报告》。

本次对接包含两个方向：

1. 上游向AI报告服务提供班组、组长及班次归属信息。
2. AI报告服务向上游回传第四份报告内容。

现有三份报告字段保持不变，新增字段采用向后兼容方式接入。

## 二、现有接口

### 2.1 日报拉参接口

```http
GET /report/ai-agent/lean-morning-daily/param
```

现有请求参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `workshopId` | Integer | 是 | 车间ID |
| `procedureId` | Integer | 是 | 工序ID |
| `reportDate` | String | 是 | 报告日期，格式 `YYYY-MM-DD` |

请求示例：

```http
GET /report/ai-agent/lean-morning-daily/param?workshopId=2&procedureId=1&reportDate=2026-07-19
```

### 2.2 报告完成回调接口

```http
POST /report/ai-agent/callback/complete
Content-Type: application/json
```

现有主要回调字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `reportId` | Integer | 上游报告任务ID |
| `status` | String | `0`成功，`1`失败 |
| `markdownContent` | String | 第一份基础日报 |
| `summaryMarkdown` | String | 第二份趋势分析 |
| `kbReportMarkdown` | String | 第三份改善建议 |
| `knowledgeBasePayload` | String | 第三份报告知识库引用信息 |
| `agentResponseRaw` | String | AI服务生成报告的原始结果 |
| `errorMessage` | String | 失败信息 |

## 三、本次接口调整范围

### 3.1 拉参响应增加班组上下文

建议在日报参数根节点增加：

```text
teamScheduleContext
```

该字段描述指定生产日期和工序下，白班、夜班分别对应的班组、组长和设备范围。

### 3.2 回调请求增加第四份报告

建议在成功回调中增加：

```text
teamLeaderMarkdown
```

该字段保存第四份《班组组长绩效对比分析报告》的Markdown内容。

### 4.2 `teamScheduleContext`字段说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `productionDate` | String | 是 | 生产日期，格式 `YYYY-MM-DD` |
| `lineId` | Integer | 是 | 产线ID，应与 `meta.lineId` 一致 |
| `mappingSource` | String | 否 | 班组信息来源，正式接口建议填写 `upstream` |
| `teams` | Array | 是 | 当日班组排班数组 |

### 4.3 `teams`字段说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `teamId` | Integer/String | 是 | 班组唯一标识 |
| `teamName` | String | 是 | 班组名称，不建议在名称中拼接组长 |
| `leaderId` | Integer/String | 建议 | 组长唯一标识，用于解决重名、调岗问题 |
| `leaderName` | String | 是 | 当班组长姓名 |
| `classId` | Integer/String | 是 | 班次ID |
| `className` | String | 是 | 班次名称，如白班、夜班 |
| `classCode` | String | 是 | 标准班次编码：`DAY`或`NIGHT` |
| `staffCount` | Integer | 建议 | 当班实际或应排人数 |
| `startTime` | String | 建议 | 班次开始时间，格式 `HH:mm` |
| `endTime` | String | 建议 | 班次结束时间，格式 `HH:mm` |
| `devices` | Array | 是 | 当班负责的设备列表 |

### 4.4 `devices`字段说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `deviceId` | Integer/String | 是 | 设备ID，应与日报业务数据中的设备ID一致 |
| `deviceName` | String | 是 | 设备名称 |

## 五、字段约束

### 5.1 生产日期

以下字段应保持一致：

```text
meta.period
teamScheduleContext.productionDate
接口请求参数 reportDate
```

夜班跨自然日时，仍按照生产日期返回。

例如：

```text
生产日期：2026-07-19
夜班时间：2026-07-19 18:00—2026-07-20 06:00
```

2026-07-20 02:00发生的夜班事件仍归属于2026-07-19生产日。

### 5.2 产线和工序

建议满足：

```text
teamScheduleContext.lineId = meta.lineId
```

如果一个工序对应多条产线，应明确返回班组负责的实际 `lineId`，不建议只依赖名称匹配。

### 5.3 班次编码

统一使用：

| 班次 | `classCode` |
|---|---|
| 白班、早班 | `DAY` |
| 夜班、晚班 | `NIGHT` |

单班制可以使用：

```json
{
  "className": "早班（单班次）",
  "classCode": "DAY"
}
```

AI报告服务发现只有一个有效班次时，仅分析已有班次，不强制生成白夜班优劣结论。

### 5.4 班组唯一性

同一生产日期、同一产线、同一设备、同一班次原则上只能归属一个班组：

```text
productionDate + lineId + deviceId + classCode
```

不应对应多个不同的 `teamId`。

### 5.5 组长信息

正式接口必须独立提供：

```text
leaderId
leaderName
```

不建议继续使用：

```text
铸带线A班组(陈明浪)
```

组长代班时，应返回当天实际负责的组长，而不是班组默认组长。

## 六、过渡阶段处理

正式拉参接口尚未提供 `teamScheduleContext` 时，AI报告服务暂时读取班组配置文件，并按照以下条件匹配：

```text
生产日期 + lineId + 班次
```

临时取值优先级：

1. 拉参响应中的 `teamScheduleContext`。
2. AI服务本地班组配置。
3. 两种来源均不存在时，标记班组信息缺失。

正式接口上线后，AI服务将优先使用上游返回的数据，本地配置仅作为过渡或容错来源。

## 七、报告完成回调

### 7.1 成功回调

建议回调请求增加：

```text
teamLeaderMarkdown
```

完整示例：

```json
{
  "reportId": 10001,
  "status": "0",
  "markdownContent": "第一份基础日报Markdown",
  "summaryMarkdown": "第二份趋势分析Markdown",
  "kbReportMarkdown": "第三份改善建议Markdown",
  "knowledgeBasePayload": "[]",
  "teamLeaderMarkdown": "第四份班组组长绩效对比报告Markdown",
  "agentResponseRaw": "{\"reports\": []}"
}
```

### 7.2 新增字段说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `teamLeaderMarkdown` | String | 成功时建议必填 | 第四份班组组长绩效对比报告 |

### 7.3 失败回调

整体任务失败时继续使用现有结构：

```json
{
  "reportId": 10001,
  "status": "1",
  "errorMessage": "报告生成失败原因"
}
```

### 7.4 第四份报告单独失败

建议第四份报告生成失败但前三份成功时：

- 整体任务仍可按照现有策略标记成功。
- `teamLeaderMarkdown`填写可识别的失败说明。
- `agentResponseRaw`保留第四份报告的错误详情。

示例：

```json
{
  "reportId": 10001,
  "status": "0",
  "markdownContent": "第一份报告",
  "summaryMarkdown": "第二份报告",
  "kbReportMarkdown": "第三份报告",
  "teamLeaderMarkdown": "班组信息缺失，无法生成组长绩效对比报告",
  "knowledgeBasePayload": "[]",
  "agentResponseRaw": "{\"reports\": []}"
}
```

## 八、向后兼容要求

### 8.1 拉参接口

`teamScheduleContext`作为可扩展字段加入：

- 旧版AI服务忽略该字段，不影响前三份报告。
- 新版AI服务在字段存在时使用。
- 字段缺失时，新版AI服务回退到临时班组配置。

### 8.2 回调接口

上游接口应允许新增的 `teamLeaderMarkdown`：

- 上游未完成页面展示时，也应允许接收并保存该字段。
- 不应因为请求体出现新增字段而返回参数错误。
- 原有三个报告字段的名称和含义保持不变。

### 8.3 空值处理

- 没有班组数据时，字段可以为空字符串或业务提示文本。
- `null`、空字符串和字段缺失均不能解释为绩效为零。
- 建议上游页面显示“暂无班组绩效报告”，而不是显示空白异常页。

## 九、数据校验及错误处理

AI报告服务将在生成第四份报告前进行以下校验：

1. `productionDate`是否与日报日期一致。
2. `lineId`是否与日报产线一致。
3. 是否至少存在一个有效班组。
4. `teamId`、`teamName`、`leaderName`是否完整。
5. `classCode`是否为 `DAY`或`NIGHT`。
6. 同班次、同设备是否存在重复班组。
7. 班组设备是否能够与日报设备匹配。
8. 是否具备白夜班直接对比条件。

异常处理：

| 异常 | 处理方式 |
|---|---|
| 缺少整个班组字段 | 前三份正常生成，第四份提示数据缺失 |
| 只有一个班次 | 只分析已有班次，不做白夜班排名 |
| 组长姓名缺失 | 显示班组，提示组长信息缺失 |
| 设备无法匹配 | 不跨设备猜测，说明匹配范围不足 |
| 同一设备重复归属 | 停止该设备的组长归属并记录数据异常 |
| 日期或产线不一致 | 不使用该班组数据 |

## 十、联调场景

上游需准备以下测试数据：

### 场景一：正常白夜班

- 两个班组。
- 人员数量相同。
- 设备范围相同。
- 白班、夜班业务数据完整。

预期：正常生成完整的组长绩效对比报告。

### 场景二：只有白班

- 只返回 `DAY`班组。
- 日报仅有白班数据。

预期：第四份报告只分析白班，并说明不具备白夜班对比条件。

### 场景三：班组信息缺失

- 不返回 `teamScheduleContext`。
- AI服务也没有对应的临时配置。

预期：前三份报告正常；第四份报告提示班组信息缺失。

### 场景四：夜班跨日

- 生产日期为当日。
- 夜班数据包含次日凌晨事件。

预期：次日凌晨事件归属前一生产日夜班。

### 场景五：设备范围不同

- 白班和夜班负责设备不完全一致。

预期：按共同设备进行对比，并提示比较口径差异。

### 场景六：组长代班

- `teamId`不变。
- `leaderId`、`leaderName`为当天代班人员。

预期：报告归属当天实际组长。

### 场景七：第四份报告单独失败

- 前三份报告正常。
- 第四份报告因班组数据异常无法生成。

预期：回调仍包含前三份报告，第四字段返回明确提示。

## 十一、联调验收清单

### 11.1 拉参验收

- [ ] 拉参响应包含 `teamScheduleContext`。
- [ ] 日期与请求参数一致。
- [ ] `lineId`与日报产线一致。
- [ ] 白班、夜班编码统一。
- [ ] 班组和组长字段完整。
- [ ] 设备ID与日报业务数据一致。
- [ ] 夜班跨日归属正确。
- [ ] 代班组长能够按日期正确返回。

### 11.2 回调验收

- [ ] 上游接口接受 `teamLeaderMarkdown`。
- [ ] 回调新增字段不会影响原有字段。
- [ ] 第四份报告能够正确保存。
- [ ] Markdown内容可以正常展示。
- [ ] 第四份为空或失败时页面有合理提示。
- [ ] 重复回调能够覆盖更新报告内容。

### 11.3 回归验收

- [ ] 原有基础日报正常。
- [ ] 原有趋势分析正常。
- [ ] 原有改善建议正常。
- [ ] 傍晚版日报仍只生成基础日报。
- [ ] 没有班组数据的旧请求仍能正常处理。

## 十二、双方职责建议

### 12.1 上游系统

- 提供正式的班组、组长、班次和设备归属数据。
- 保证生产日期和夜班跨日口径一致。
- 接收并保存 `teamLeaderMarkdown`。
- 根据需要增加第四份报告页面展示。

### 12.2 AI报告服务

- 兼容临时班组配置和正式接口字段。
- 校验班组数据后生成第四份报告。
- 缺少数据时不虚构组长或绩效结论。
- 将第四份报告保存到本地数据库。
- 通过回调接口返回 `teamLeaderMarkdown`。

## 十三、待双方确认事项

1. 拉参响应是否采用根节点 `teamScheduleContext`。
2. 班组唯一标识和组长唯一标识的数据类型。
3. 上游是否能够直接提供 `classCode`。
4. 夜班生产日期归属规则是否统一为前一日。
5. 上游回调是否采用 `teamLeaderMarkdown`。
6. 第四份报告单独失败时整体任务状态如何定义。
7. 上游何时增加第四份报告的存储字段和页面页签。
8. 正式班组字段上线前，班组配置文件由哪一方维护。

## 十四、建议最终字段

| 数据方向 | JSON字段 | 数据库字段 | 说明 |
|---|---|---|---|
| 上游 → AI服务 | `teamScheduleContext` | — | 班组排班上下文 |
| AI服务内部 | — | `team_leader_markdown` | 第四份报告存储字段 |
| AI服务 → 上游 | `teamLeaderMarkdown` | 由上游确定 | 第四份报告回调内容 |
