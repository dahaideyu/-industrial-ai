# AI 报告生成系统 - 数据预处理方案

## 一、背景与痛点

### 1.1 业务现状

当前 AI 报告生成系统需要处理来自 MES 系统的多维度生产数据，包括：
- **点检保养任务数据**：设备点检记录、执行状态、异常明细
- **设备告警数据**：故障报警、停机时长、故障代码
- **参数报警数据**：工艺参数偏差、报警等级、处理状态

### 1.2 核心痛点

| 痛点 | 影响 | 量化指标 |
|------|------|----------|
| **数据量大** | 单次报告原始数据达数万字符 | 3-5 万字符/次 |
| **LLM 统计不准** | 大模型对大量数据的计数、汇总容易出错 | 错误率约 15-20% |
| **Token 消耗高** | 冗余字段占用上下文，增加调用成本 | 成本增加 40%+ |
| **分析效率低** | 大量无关字段干扰 LLM 分析重点 | 响应时间延长 |

---

## 二、解决方案

### 2.1 核心思想

> **将统计计算交给 Python，让 LLM 专注于分析洞察**

采用"**数据预处理 + AI 分析**"的两阶段架构：
1. **Python 层**：精确统计、数据聚合、压缩上下文
2. **LLM 层**：趋势分析、根因推断、改进建议

### 2.2 架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                    原始 MES 数据                              │
│  (点检保养、设备告警、参数报警、生产数据...)                    │
└─────────────────────┬───────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────┐
│              第一层：数据清洗 (data_cleaner.py)                │
│  • 递归删除空值字段（"" / null / None）                        │
│  • 过滤无关 sourceKey（车间树、工序列表等）                     │
│  • 剥离 HTTP 包装层（requestUrl / msg / code）                │
└─────────────────────┬───────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────┐
│              第二层：数据预处理 (data_preprocessor.py)          │
│  • 按 sourceKey 前缀匹配预处理器                              │
│  • Map-Reduce 变换：聚合统计 + 压缩上下文                     │
│  • 输出结构化摘要（summary / byDevice / abnormalDetails）     │
└─────────────────────┬───────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────┐
│              第三层：AI 报告生成 (report_generator.py)          │
│  • 注入预处理后的精简数据                                     │
│  • LLM 专注分析趋势、根因、改进措施                           │
│  • 流式输出报告内容                                          │
└─────────────────────────────────────────────────────────────┘
```

## 三、技术实现

### 3.1 数据清洗层

**文件位置**：`backend/utils/data_cleaner.py`

**核心功能**：

```python
# 三步清洗流程
cleaned = clean_raw_data(raw_data)
# 步骤1: 递归删除空值字段
# 步骤2: 过滤指定 sourceKey（workshopTree_、mesProcedureList_ 等）
# 步骤3: 剥离 HTTP 包装层
```

**清洗效果**：
- 删除空值字段，减少 10-15% 数据量
- 过滤无关 sourceKey，聚焦业务数据
- 展开嵌套结构，简化数据访问

### 3.2 数据预处理层

**文件位置**：`backend/utils/data_preprocessor.py`

**设计模式**：**注册器模式 + 策略模式**

```python
# 预处理器注册机制
@register("maintainTaskPage_")
def prep_maintain_task(data: dict) -> dict | None:
    """点检保养 → 按设备分组统计状态×执行结果"""
    # 输入：原始 records[] 数组
    # 输出：summary + byDevice + abnormalDetails
    ...
```

**扩展方式**：
- 使用 `@register("sourceKeyPrefix_")` 装饰器注册新预处理器
- 按前缀匹配，一个 sourceKey 只匹配一个预处理器
- 返回 `None` 表示跳过该数据源
- **跨 sourceKey 合并**：支持将多个独立的设备数据合并为一个对象，减少重复结构

### 3.3 已实现的预处理器

**输出结构**：

{
  "summary": {

**核心价值**：

#### ④ 月度运转率合并 (`deviceMonthRunningRate_`)

**问题背景**：
- 7 台设备，每台设备独立返回月度运转率数据（`deviceMonthRunningRate_d48`、`deviceMonthRunningRate_d49`...）
- 每个数据源都包含相同的日期轴（`xaxis`，30 天）和图表名称（`chartNames`）
- **重复存储导致数据冗余**：7 个设备 × 30 天日期 = 210 个重复日期字符串

**合并方案**：
```python
# 合并前：7 个独立对象，每个都包含完整的 xaxis
{
  "sourceKey": "deviceMonthRunningRate_d48",
  "data": {
    "avgRunningRate": 99.6,
    "chartDataVoList": [
      {"chartName": "运转率", "xaxis": ["2026-06-01", ...], "seriesData": [96.6, ...]},
      {"chartName": "待机率", "xaxis": ["2026-06-01", ...], "seriesData": [...]},
      {"chartName": "故障率", "xaxis": ["2026-06-01", ...], "seriesData": [...]}
    ]
  }
}
# × 7 个设备 = 14.8 KB

# 合并后：1 个对象，提取公共 xaxis，每个设备只保留 seriesData
{
  "sourceKey": "deviceMonthRunningRate_merged",
  "data": {
    "xaxis": ["2026-06-01", ...],  // 公共日期轴（只存一份）
    "chartNames": ["运转率", "待机率", "故障率"],  // 公共图表名
    "devices": {
      "48": {
        "avgRunningRate": 99.6,
        "targetOperationRate": 80,
        "chartDataVoList": [
          {"seriesData": [96.6, ...]},  // 只保留 seriesData
          {"seriesData": [...]},
          {"seriesData": [...]}
        ]
      },
      "49": { ... },
      // ... 共 7 个设备
    }
  }
}
# = 3.5 KB
```

**核心价值**：
- **数据压缩**：14.8 KB → 3.5 KB，压缩率 **76.4%**
- **结构优化**：提取公共 xaxis，消除重复存储
- **保持完整**：每个设备的汇总字段（avgRunningRate、targetOperationRate 等）完整保留

#### ⑤ 日运转率合并 (`deviceDayRunningRate_`)

**问题背景**：
- 7 台设备，每台设备独立返回日运转率数据（`deviceDayRunningRate_d48`、`deviceDayRunningRate_d49`...）
- 每个数据源都包含班次结构（白班/夜班）和运转率详情
- **合并后便于跨设备对比分析**

**合并方案**：
```python
# 合并前：7 个独立对象
{
  "sourceKey": "deviceDayRunningRate_d48",
  "data": {
    "avgRunningRate": 94.6,
    "childrenRunningRates": [
      {"name": "7点白班", "avgRunningRate": 100, "runningDuration": 43200, ...},
      {"name": "19点夜班", "avgRunningRate": 73.8, "runningDuration": 8335, ...}
    ]
  }
}
# × 7 个设备 = 6.3 KB

# 合并后：1 个对象，按设备ID组织
{
  "sourceKey": "deviceDayRunningRate_merged",
  "data": {
    "devices": {
      "48": {
        "avgRunningRate": 94.6,
        "childrenRunningRates": [
          {"name": "7点白班", "avgRunningRate": 100, ...},
          {"name": "19点夜班", "avgRunningRate": 73.8, ...}
        ]
      },
      "49": { ... },
      // ... 共 7 个设备
    }
  }
}
# = 5.0 KB
```

**核心价值**：
- **数据压缩**：6.3 KB → 5.0 KB，压缩率 **20.9%**
- **结构优化**：统一设备数据入口，便于批量分析
- **便于对比**：所有设备数据在同一对象中，支持跨设备对比

### 5.1 可扩展的架构设计

**设计亮点**：

- **向后兼容**：合并后的数据结构保持 `_preprocessed: true` 标记

**技术价值**：
- 支持多个独立数据源的智能合并
- 消除重复存储，大幅减少数据量

## 七、附录：跨 sourceKey 合并技术实现

### 7.1 合并架构

```python
def preprocess_sources(response_list: list) -> list:
    """遍历 response[]，对匹配到的 sourceKey 执行预处理并替换 item["data"]。

    Args:
        response_list: clean_raw_data 之后的 response 数组，原地修改

    Returns:
        同 response_list（原地修改后的引用）
    """
    # 第一步：执行单 sourceKey 预处理器
    for item in response_list:
        if not isinstance(item, dict):
            continue
        sk = item.get("sourceKey", "")
        for prefix, preprocessor in PREPROCESSOR_REGISTRY.items():
            if sk.startswith(prefix):
                old_data = item.get("data", {})
                if isinstance(old_data, (dict, list)):
                    new_data = preprocessor(old_data)
                    if new_data is not None:
                        new_data["_preprocessed"] = True
                        item["data"] = new_data
                break

    # 第二步：执行跨 sourceKey 合并
    _merge_device_running_rates(response_list)

    return response_list
```

### 7.2 合并流程

```python
def _merge_device_running_rates(response_list: list) -> None:
    """合并 deviceMonthRunningRate_d* 和 deviceDayRunningRate_d* 数据。

    将多个独立的设备数据合并为一个对象，提取公共数据（如 xaxis）减少重复。
    合并后删除原始的独立 sourceKey 项。
    """
    _merge_device_month_running_rates(response_list)
    _merge_device_day_running_rates(response_list)
```

### 7.3 合并算法

**月度运转率合并**：
1. 收集所有 `deviceMonthRunningRate_d*` 项
2. 提取公共 `xaxis` 和 `chartNames`
3. 遍历每个设备，只保留 `seriesData`（删除重复的 `xaxis`）
4. 构造合并后的 `devices` 对象
5. 删除原始项，添加合并后的项

**日运转率合并**：
1. 收集所有 `deviceDayRunningRate_d*` 项
2. 遍历每个设备，保留完整的班次数据
3. 构造合并后的 `devices` 对象
4. 删除原始项，添加合并后的项

### 7.4 索引删除策略

```python
# 删除原始项（从后往前删，避免索引偏移）
indices_to_remove = sorted([i for i, _ in items_to_merge], reverse=True)
for idx in indices_to_remove:
    response_list.pop(idx)

# 添加合并后的项
response_list.append({
    "sourceKey": "deviceMonthRunningRate_merged",
    "requestUrl": "",
    "data": merged_data,
})
```
