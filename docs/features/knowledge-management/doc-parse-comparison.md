# 文档解析方案对比

## 方案概述

### 方案A：宋总方案（Git + PaddleOCR）

```
文档上传
  → Git 管理版本
  → 统一转 PDF（所有格式 → LibreOffice 或类似工具）
  → PaddleOCR 视觉识别（文字 + 图片 + 位置信息，本地部署）
  → Python 代码解析 PDF（提取文本结构、表格、图表）
  → 解析结果元数据标注 + Git 管理版本
  → 大模型整理（OCR结果 + 代码解析结果作为上下文）
  → 完整解析文档
```

### 方案B：当前知识库系统（MinIO + MarkItDown）

```
文档上传
  → MinIO 对象存储 + DB 记录版本
  → 格式处理分支：
      ├── PDF：直接复用原文件，MarkItDown 提取文本
      ├── Word/PPT：LibreOffice 转 PDF，MarkItDown 提取
      ├── Excel：openpyxl 转 HTML（保留样式/合并单元格/多Sheet）
      ├── 图片：Tesseract OCR 识别
      └── 图纸(PDF)：AI视觉模型（qwen-vl-plus）逐页解析 → 生成说明文档
  → 文本提取：MarkItDown（保留标题/列表/表格等Markdown结构）
      └── 低文本量/乱码时自动触发 Tesseract OCR
  → AI审核评分（DeepSeek）：
      ├── 关联性评分（是否匹配收集要求）
      ├── 质量评分（内容完整性、可操作性）
      └── 版本对比（新旧版本差异分析 + 重复检测）
  → DB 存储评分 + MinIO 存储文件
```

---

## 详细对比

### 1. 版本管理

| 维度 | 方案A（Git） | 方案B（MinIO + DB） |
|------|-------------|---------------------|
| **存储方式** | Git 仓库存储所有版本 | MinIO 对象存储每个版本独立文件 |
| **版本历史** | `git log` 完整提交历史 | DB `knb_document_versions` 表记录 |
| **差异对比** | `git diff` 原生支持 | difflib Python库文本对比 |
| **回滚** | `git checkout` 一键恢复 | 手动调API删除当前版、激活旧版 |
| **协作** | 天然支持多人协同（分支/合并） | DB加锁，单用户操作 |
| **存储效率** | delta压缩，只存差异 | 每个版本完整文件（空间 = 版本数 × 文件大小） |
| **二进制文件** | Word/Excel/PDF delta压缩效果差，仓库易膨胀 | 不受影响，每个文件独立存储 |
| **权限管理** | Git 权限 + 仓库权限 | DB 用户认证 + MinIO ACL |
| **审计追溯** | `git log --author` 清晰 | DB `uploaded_by` 字段，简单 |

**总结：方案A在文本类文档的版本管理上有明显优势，方案B对二进制大文件更友好，架构更简单。**

---

### 2. 文件格式处理

| 维度 | 方案A | 方案B |
|------|-------|-------|
| **处理策略** | 统一转 PDF，单一流水线 | 按文件类型分支处理 |
| **Word/PPT** | 转 PDF | 转 PDF |
| **Excel** | 转 PDF（❌ 效果差） | 转 HTML（✅ 保留样式/合并单元格/多Sheet） |
| **PDF** | 直接解析 | 直接解析 |
| **图片** | 包含在 PDF 页中处理 | 独立 Tesseract OCR |
| **图纸** | 作为普通 PDF 页处理 | 独立AI视觉模型流水线（4步解析） |
| **处理复杂度** | 简单统一，维护成本低 | 多分支流水线，更精细 |
| **Excel 支持** | ❌ 转PDF后表格丢失 | ✅ HTML 保留格式 |
| **图纸智能解析** | ❌ 没有专门支持 | ✅ AI视觉模型（qwen-vl-plus）逐页解析 |

**总结：方案A统一处理简单但缺乏针对性（尤其Excel效果差），方案B精细分工但维护成本更高。**

---

### 3. OCR / 文本提取

| 维度 | 方案A（PaddleOCR） | 方案B（MarkItDown + Tesseract） |
|------|-------------------|-------------------------------|
| **OCR引擎** | 本地部署 PaddleOCR | Docker Tesseract（容器内） |
| **识别能力** | 文字 + 图片 + **位置信息** | 纯文本 OCR |
| **中文支持** | ✅ 优秀（百度出品） | ⚠️ 一般（需 chi_sim 语言包） |
| **位置信息** | ✅ 保留坐标/bounding box | ❌ 不保留 |
| **表格识别** | ✅ PP-Structure 表格识别 | ❌ 不支持 |
| **版面分析** | ✅ Layout分析 | ❌ 不支持 |
| **部署方式** | 本地 Python（无容器依赖） | Docker Tesseract + pydub |
| **资源占用** | CPU/GPU 可选，模型较大 | 轻量，几MB |
| **扫描件处理** | ✅ 专为扫描件设计 | ⚠️ 需手动勾选"强制OCR" |
| **文本提取技术** | PaddleOCR + Python解析 | MarkItDown（Microsoft开源） |
| **格式保留** | ❌ 不保留（OCR输出纯文本） | ✅ 保留Markdown结构（标题/表格） |
| **低质量文本** | 完全依赖 OCR | 先试文本提取，失败再 OCR |

**总结：方案A的PaddleOCR强大但重，方案B轻量但OCR能力有限。如果大量处理扫描件/图纸，PaddleOCR更好；如果大量是原生电子文档，MarkItDown更高效。**

---

### 4. 大模型整合

| 维度 | 方案A | 方案B |
|------|-------|-------|
| **模型用途** | 整理OCR+解析结果为完整文档 | AI审核评分 + 版本对比 |
| **输入** | OCR文本 + Python解析结构 + 位置信息 + 元数据 | 收集要求 + 提取文本 + 旧版本diff |
| **输出** | 结构化完整文档 | 评分结果（关联性/质量/改进度）+ 评价说明 |
| **调用次数** | 每文档1次（整理） | 每版本1次（审核），多次重试 |
| **超时处理** | 未说明 | 最多3次重试，每次180s |
| **版本对比** | Git diff 交给大模型理解 | difflib + prompt 嵌入版本差异 |
| **元数据标注** | ✅ 主动标注 | ✅ AI评分即标注 |

**总结：方案A用大模型做"产出"（生成结构化文档），方案B用大模型做"审核"（评分+评价）。用途不同，互补而非替代。**

---

### 5. 架构复杂度

| 维度 | 方案A | 方案B |
|------|-------|-------|
| **外部服务** | PaddleOCR（本地Python） + Git Server | MinIO + PostgreSQL + Redis + LibreOffice + Celery + Tesseract |
| **Docker 容器** | 1-2个（Git Server可选） | 6个（MinIO/PostgreSQL/Redis/LibreOffice/Celery/应用） |
| **存储层** | Git 仓库 | MinIO + PostgreSQL |
| **消息队列** | 无（同步处理？） | Redis（Celery异步任务） |
| **部署难度** | 较低 | 较高 |
| **可扩展性** | Git 仓库数量随项目增长 | 水平扩展（Celery多Worker） |
| **故障容错** | Git 单点 | Celery 队列重试 + Worker 多实例 |

**总结：方案A架构更简单但功能单一，方案B功能完整但部署运维复杂。**

---

## 优缺点总结

### 方案A（Git + PaddleOCR）

**优点：**
- 版本管理天然支持，diff/回滚/分支/合并都很自然
- PaddleOCR 识别能力强，支持版面分析、表格识别、位置信息
- 统一转 PDF 简化处理流水线
- 本地部署，无外部服务依赖，离线可用
- 架构简单，运维成本低
- Git 存储省空间（delta 压缩）

**缺点：**
- Excel 转 PDF 效果极差（表格断裂、样式丢失）
- PaddleOCR 模型较大，资源占用高
- 纯 OCR 方案对原生电子文档效率低（明明直接提取更快）
- 缺少专门的图纸解析（PLC/电气图）
- 缺少异步任务机制，大文档可能阻塞
- 缺少 AI 审核评分体系
- 二进制大文件（PDF 图纸）在 Git 中管理不佳

### 方案B（MinIO + MarkItDown）

**优点：**
- 按文件类型分支处理，Excel 转 HTML 保留格式
- 专门的图纸解析流水线（AI视觉模型 + 宏观梳理）
- 异步任务（Celery），大文件不阻塞
- AI 审核评分体系完整（关联性/质量/版本改进）
- MarkItDown 保留文档结构（标题/列表/表格）
- 成熟的部署方案（Docker Compose 一键启动）
- MinIO 对二进制大文件友好

**缺点：**
- 无版面分析能力，不保留 OCR 位置信息
- 中文 OCR 能力一般
- 版本管理笨重（完整文件存储，空间浪费）
- 版本 diff 能力弱（仅 difflib 文本对比）
- 部署复杂（多个Docker服务）
- 无 Git 分支/协同能力

---

## 融合建议

两个方案并非互斥，可以取长补短：

| 改进点 | 建议 |
|--------|------|
| **版本管理** | 对本文类文档（Markdown、说明文档）引入 Git 管理，减少 MinIO 存储冗余 |
| **OCR 增强** | 对扫描件/图纸预处理环节，替换 Tesseract 为 PaddleOCR，提升中文识别和版面分析 |
| **Excel 处理** | 当前方案已优于方案A（HTML 格式保留），保持 |
| **图纸解析** | 当前方案独有优势（AI 视觉模型），保持 |
| **异步任务** | 当前方案已完备（Celery），保持 |
| **位置信息** | 可引入 PaddleOCR 的 Layout 分析结果作为 AI 审核的额外输入 |
