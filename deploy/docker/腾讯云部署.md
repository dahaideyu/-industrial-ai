# 腾讯云部署（参数分析，不含 RAGFlow）

目标：4核4G / 70G 的 CVM 上，只把**设备参数分析**这套跑起来。
知识库、智能问答、RAGFlow 全部不部署。

---

## 只起三个服务

| 服务 | 作用 | 为什么需要 |
|------|------|-----------|
| `industrial-ai` | 后端 API + 前端 + nginx | 主应用 |
| `postgresql` | TimescaleDB | 参数数据存这里 |
| `mqtt-etl` | 订阅 MQTT 写库 | 传感器数据入口，不起就没有新数据 |

**不起**（省内存，参数分析不依赖）：

| 服务 | 属于什么功能 | 不起的影响 |
|------|-------------|-----------|
| `redis` | Celery 队列 | 无。`device_param` 模块不碰 redis |
| `minio` | 知识库文档存储 | 无。同上 |
| `knb-celery-worker` | 知识库异步任务 | 无。顺带省掉一个含 LibreOffice+OCR 的镜像（约 2GB） |
| `repair-suggestion` | 维修建议页面 | 「维修建议」菜单不可用，其余正常。需要就加进 `DEPLOY_SERVICES` |

脚本里已固化：

```bash
DEPLOY_SERVICES="industrial-ai postgresql mqtt-etl"
BUILD_SERVICES="industrial-ai mqtt-etl"     # postgresql 是拉的官方镜像
```

要全量部署：`DEPLOY_SERVICES="" BUILD_SERVICES="" ./auto-deploy.sh --force`

## 一、服务器准备

```bash
# 1. 加 swap（4G 机器构建时的保险，必做）
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 2. 目录与外部卷
sudo mkdir -p /data/industrial-ai/{config,appdata,logs,dead_letter,backup,deploy-state}
sudo chown -R $USER:$USER /data/industrial-ai
docker volume create industrial_pgdata
docker volume create industrial_minio      # 不起 minio 也建一下，compose 解析要用

# 3. 拉代码
sudo mkdir -p /opt/industrial-ai && sudo chown -R $USER:$USER /opt/industrial-ai
git clone https://gitee.com/dahaideyu/industrial-ai.git /opt/industrial-ai
cd /opt/industrial-ai && git remote rename origin gitee && git checkout dev
```

## 二、配置文件

```bash
cp /opt/industrial-ai/deploy/docker/.env.example /data/industrial-ai/config/.env
vi /data/industrial-ai/config/.env
chmod 600 /data/industrial-ai/config/.env
```

### 必填项

```bash
# ── 数据库：容器内用服务名，不是 localhost ──
PG_HOST=postgresql          # ← 容器网络里的服务名
PG_PORT=5432                # ← 容器内部端口，不是宿主机映射的 15432
PG_DB=knowledge_base
PG_USER=zxzz
PG_PASSWORD=<自己设一个强口令>
PG_SSLMODE=disable    # 同一 docker 网络内不需要 SSL

# ── 大模型（AI 分析/诊断要用）──
PROVIDER=deepseek
DEEPSEEK_API_KEY=<你的 key>

# ── MQTT（传感器数据来源）──
MQTT_BROKER=<broker 地址>
MQTT_PORT=1883
MQTT_TOPIC=<工艺点位 topic>
MQTT_TOPIC_NH=<能耗 topic>
MQTT_USER=
MQTT_PASS=

# ── 关掉用不到的模块 ──
ENABLE_SQL_QA=false
ENABLE_KNOWLEDGE_BASE=false
ENABLE_REPORT_SCHEDULER=false   # 早会/质量/效率报告的定时任务，先不用就关掉

# ── RAGFlow 留空即可 ──
RAGFLOW_BASE_URL=
RAGFLOW_API_KEY=
DEVICE_PARAM_KB_CHAT_ID=
```

RAGFlow 留空是安全的：`analysis_service.py` 里 `if not chat_id: return None`，
调用失败也被捕获并打印「知识库查询失败（不影响分析）」，AI 分析照常出结果，
只是少了工艺文档参考。

### ⚠️ 一个必须设、否则 compose 直接报错的坑

`docker-compose.yml` 里这两行用了 `:?` 语法：

```yaml
POSTGRES_PASSWORD: ${PG_PASSWORD:?请在 .env 中设置 PG_PASSWORD}
MINIO_ROOT_PASSWORD: ${MINIO_SECRET_KEY:?请在 .env 中设置 MINIO_SECRET_KEY}
```

compose 在**解析整个文件**时就会做变量插值，跟 profile、跟你起不起这个服务无关。
所以哪怕根本不打算跑 minio，`.env` 里也必须有 `MINIO_SECRET_KEY=`（随便填一个值），
否则 `docker compose` 会直接报错退出，什么都起不来。

## 三、首次启动 —— 一条命令

前面「一、服务器准备」里的 swap／目录／数据卷，脚本会自动做，不用手工执行。
真正需要你手动做的只有两件：**装 docker** 和 **填 .env**。

```bash
cd /opt/industrial-ai/deploy/docker/scripts
chmod +x setup-tencent.sh

# 第一次跑：如果 .env 还不存在，会从模板生成并提示你去填，然后退出
./setup-tencent.sh

# 填好 /data/industrial-ai/config/.env 之后再跑一次，这次会一路装到底
./setup-tencent.sh
```

脚本按顺序做六件事，任何一步不过就停下来并说清楚原因：

| 步骤 | 内容 | 不过时的表现 |
|------|------|-------------|
| 1 环境体检 | docker / compose v2 / 用户权限 / 内存 / 磁盘 | 缺什么报什么，并给出修复命令 |
| 2 swap | 没有就建 4G 并写入 fstab | 已有则跳过 |
| 3 目录与卷 | 建 `/data/industrial-ai/*` 和两个外部卷 | 已存在则跳过，**不会动已有数据** |
| 4 配置校验 | 必填项是否为空、是否还是 `your-xxx` 占位符 | 逐项列出哪个没填 |
| 5 compose 校验 | `docker compose config` 能否解析 | 打印具体错误 |
| 6 分阶段启动 | 先起库等就绪 → 再构建起应用 → 健康检查 | 失败时自动打印最近 40 行日志 |

常用参数：

```bash
./setup-tencent.sh --check          # 只体检，不改任何东西（上线前先跑这个最稳）
./setup-tencent.sh --no-swap        # 已自行配过 swap
./setup-tencent.sh --all-services   # 连 redis/minio/worker/维修建议一起起
```

脚本**可重复执行**：已建的目录、卷、swap 都会跳过，`.env` 不会被覆盖。
跑完会打印访问地址、验证数据入库的命令和下一步建议。

### 如果想手工分步执行

```bash
cd /opt/industrial-ai/deploy/docker

docker compose -f docker-compose.yml -f docker-compose.tencent.yml \
  --profile local-db --profile mqtt config | head -60      # 看合并后的最终配置

docker compose -f docker-compose.yml -f docker-compose.tencent.yml \
  --profile local-db up -d postgresql                       # 先起库
docker logs -f postgresql   # 等 "database system is ready to accept connections"

COMPILE_SOURCE=false docker compose -f docker-compose.yml -f docker-compose.tencent.yml \
  --profile local-db --profile mqtt up -d --build industrial-ai mqtt-etl

curl http://127.0.0.1:9300/api/health
```

浏览器访问 `http://<公网IP>:9300`（腾讯云安全组要放行 9300）。

# ETL 日志

## 六、以后要加 RAGFlow

RAGFlow 是独立的一套栈（Elasticsearch + MySQL + MinIO + Redis + server），
官方最低要求 16GB 内存，**不能跟本项目挤在这台 4G 机器上**。届时选：

- 单独开一台 16G 机器跑，本项目配 `RAGFLOW_BASE_URL` 指过去
- 或把这台升配到 16G

配好 `RAGFLOW_BASE_URL` / `RAGFLOW_API_KEY` / `DEVICE_PARAM_KB_CHAT_ID` 后，
知识库增强会自动生效，不需要改代码。

# 第二部分：推 Gitee dev 自动上线

## 整体流程

```
本地开发机                    Gitee                     腾讯云 CVM
    │                           │                            │
    │  push 快照到 dev          │                            │
    ├──────────────────────────>│                            │
    │                           │   每分钟 git fetch 检查     │
    │                           │<───────────────────────────┤
    │                           │                            │ 有新提交？
    │                           │                            │  ├─ 否 → 静默退出
    │                           │                            │  └─ 是 ↓
    │                           │                            │ reset --hard
    │                           │                            │ docker compose build
    │                           │                            │ up -d
    │                           │                            │ 健康检查
    │                           │                            │  ├─ 通过 → 记录版本
    │                           │                            │  └─ 失败 → 回滚上一版
```

用**轮询**而不是 WebHook 的原因：不用在 CVM 上开公网入站端口、不用配 WebHook 密钥验签、
不怕内网/安全组变动导致回调收不到。代价是最长 1 分钟延迟，对这个场景够用。
如果要秒级触发，见文末「可选：改成 WebHook 触发」。

## 一、服务器一次性配置

前置：已按 `docker-compose.tencent.yml` 头部说明挂好数据盘、建好
`/data/industrial-ai/config/.env` 和外部卷。

### 1. 拉代码到部署目录

```bash
sudo mkdir -p /opt/industrial-ai && sudo chown -R $USER:$USER /opt/industrial-ai
git clone https://gitee.com/dahaideyu/industrial-ai.git /opt/industrial-ai
cd /opt/industrial-ai

# 远程名必须叫 gitee（脚本默认用这个名字）
git remote rename origin gitee
git checkout dev
```

### 2. 让服务器能免密拉私有仓库

仓库是私有的，服务器得有凭据。推荐用 **Gitee 私人令牌**（只给读权限）：

```bash
# Gitee → 设置 → 私人令牌 → 生成新令牌，只勾 projects 读权限
git remote set-url gitee https://用户名:令牌@gitee.com/dahaideyu/industrial-ai.git

# 令牌会明文存在 .git/config 里，锁一下权限
chmod 600 /opt/industrial-ai/.git/config
```

> 更安全的做法是用 SSH 部署公钥（Gitee → 仓库 → 管理 → 部署公钥），
> 服务器只有只读权限，也不会有明文令牌落盘。

### 3. 装定时任务

**方式 A：systemd timer（推荐，有日志有重试）**

```bash
sudo cp /opt/industrial-ai/deploy/docker/scripts/systemd/industrial-ai-deploy.* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now industrial-ai-deploy.timer

# 确认
systemctl list-timers industrial-ai-deploy.timer
journalctl -u industrial-ai-deploy -f
```

**方式 B：cron（更简单）**

```bash
chmod +x /opt/industrial-ai/deploy/docker/scripts/auto-deploy.sh
crontab -e
# 加一行：
* * * * * /opt/industrial-ai/deploy/docker/scripts/auto-deploy.sh >> /data/industrial-ai/logs/auto-deploy.log 2>&1
```

### 4. 先手动跑一次验证

```bash
cd /opt/industrial-ai/deploy/docker/scripts
./auto-deploy.sh --force        # 强制走一遍完整流程
```

看到 `部署成功: <sha>` 就说明通了。

## 二、日常使用

### 本地推代码触发部署

因为 Gitee 侧用的是**不带历史的快照分支**（见 `gitee-main`），推送命令不是普通的
`git push`，而是：

```bash
# 在本地仓库执行：把当前代码做成一次新快照，推到 Gitee dev
git branch -f gitee-main $(git commit-tree HEAD^{tree} -p gitee-main -m "本次改动说明")
git push gitee gitee-main:dev
```

走公司代理时加：
`git -c http.proxy=http://127.0.0.1:3128 -c https.proxy=http://127.0.0.1:3128 push gitee gitee-main:dev`

推完最多 1 分钟，服务器就会自动开始部署。

### 看部署状态

```bash
journalctl -u industrial-ai-deploy -n 50        # systemd 方式
tail -f /data/industrial-ai/logs/auto-deploy.log # cron 方式
cat /data/industrial-ai/deploy-state/last_ok_tag # 当前线上版本
```

### 手动回滚

```bash
/opt/industrial-ai/deploy/docker/scripts/auto-deploy.sh --rollback
```

回滚是切镜像 tag，不重新构建，几秒完成。

## 三、这套机制的保护措施

| 风险 | 处理方式 |
|------|----------|
| 构建失败 | 保持旧容器运行，不动线上 |
| 新版本起不来 / 健康检查不过 | 自动切回上一个成功的镜像 tag |
| cron 每分钟触发、构建要几分钟 | 文件锁，同时只允许一个部署；锁超 1 小时自动清理 |
| Gitee 上强推过历史 | 用 `fetch + reset --hard` 而不是 `pull`，非快进也能同步 |
| 镜像堆积撑爆磁盘 | 每次部署后清理，保留最近 3 轮 |
| 部署会不会重启数据库 | 不会。`up -d` 只重建镜像/配置变了的服务，`postgresql`/`minio`/`redis` 原地不动 |

**注意**：脚本用 `git reset --hard`，服务器 `/opt/industrial-ai` 里的本地改动会被丢弃。
那个目录只当部署产物看，不要在上面直接改代码。配置在 `/data/industrial-ai/config/.env`，
不在仓库里，不受影响。

## 四、服务器构建的资源要求（4核/4G 实测评估）

**结论：4核4G 可行**，但内存余量不大，务必先加 swap。

| 资源 | 实测/估算 | 判断 |
|------|-----------|------|
| 前端 vite 构建峰值内存 | **923 MB**（本机实测） | 4G 机器可承受 |
| 构建期总内存需求 | ≈1.5–2 GB（vite + npm/pip 安装 + buildkit） | 可用 2.8G，够但不宽裕 |
| CPU | 4 核，构建约 5–10 分钟 | 够 |
| 镜像磁盘占用 | 3 个 target 合计 ≈2.5–3 GB（共享基础层） | 39G 空闲，够 |
| 流量 | 首次拉基础镜像 ≈1 GB | 600G 包，可忽略 |

镜像偏大的原因：`final-app` 和 `final-worker` 都装了 LibreOffice 全家桶
（文档预览）+ tesseract 中文 OCR，光这两项就近 1 GB。

### 必做：加 4G swap

构建时如果内存打满，OOM killer 杀掉的**未必是构建进程，可能是正在服务的
industrial-ai 容器**。swap 是廉价保险：

```bash
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

脚本里已内置内存闸门：构建前检查 `MemAvailable`，低于 1500MB 且 swap < 2GB 时
**直接跳过本次构建**（下一分钟自动重试），宁可不部署也不拖垮线上。
阈值可调：`MIN_FREE_MB=2000 ./auto-deploy.sh`

### 磁盘的真正大头是数据库，不是镜像

系统盘 31G/70G 里，绝大部分是 `device_alarm_info` 等传感器表 —— 镜像才 3G 左右。
跑完 `migrations/006_raw_retention_7d.sql`（7天保留）会释放大量空间，
之后表体积基本恒定。**先跑保留策略，再判断要不要加数据盘。**

### 更省心的替代方案：不在服务器构建

如果后续嫌构建慢/占资源，可以改成本地或 CI 构建好，推到
**腾讯云容器镜像服务 TCR（个人版免费）**，服务器只 `docker compose pull`：

- 服务器零构建负载，内存风险完全消失
- 部署从几分钟变成几十秒
- 不占构建缓存磁盘

需要的话我把 `auto-deploy.sh` 的构建段改成 pull 模式。

## 五、可选：改成 WebHook 秒级触发

轮询有最长 1 分钟延迟。想秒级的话，在服务器上加一个只监听本机的小接收端，
用 nginx 反代出去，Gitee WebHook 打这个地址：

```bash
# 极简做法：用 systemd socket + 一行 shell，收到请求就触发一次 service
# Gitee → 仓库 → 管理 → WebHooks → 添加，URL 填 https://你的域名/deploy-hook
#   密码/签名密钥务必设置，并在接收端校验，否则任何人都能触发你的部署
```

需要的话我可以把这个接收端补全（含签名校验 + 只允许 Gitee 出口 IP）。
在那之前，轮询方式已经能满足"推了就自动上线"的需求。
